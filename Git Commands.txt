// Important terms
Working Directory (Untracked files): Where we make changes to files.
Staging Area (Index): Where we stage your changes before committing.
Local Repository(Head): Where your project's version history is stored on your machine.
Remote Repository: A central repository (like GitHub) where your project’s changes are stored online.
HEAD: HEAD refers to the most recent commit made on the current branch.

// WORKING DIRECTORY -> STAGING AREA      
git add <file>          // Adds an Untracked, Modified or Deleted file from working directory to staging area
git add -A              // Add all Untracked, Modified or Deleted files from working directory to staging area



// STAGING AREA -> LOCAL REPOSITORY
git commit stores a snapshot of our changes (like modified files, added files, or deleted files) in the local repository.
git commit                      // Add commit message(all files must be in staging area for adding commit)
git commit -m "info"            // Add commit message in single line


// WORKING DIRECTORY -> LOCAL REPOSITORY 
git commit -a -m "Message"      // Skips staging area(does not include untracked files.)



// GIT STASH
git stash is a command in Git that is used to stash changes in our working directory and staging area so that we can work on something else, without making a "commit".
After running git stash, Git will take both staged and unstaged changes and store them in the "stash". Your Working directory is then reverted to the state of the last commit. So, your changes will be saved in the stash.
git stash                       // This stashes both staged and unstaged changes.
git stash save "message"        // You can include a custom message to help identify the stash later.
git stash lists                 // Shows a list of all stashes in your repository. Each stash is indexed with a name.
git stash pop                   // Applies the changes from the most recent stash and removes it from stash list.
git stash pop [stash_name]      // Applies the changes from a specific stash and removes it from the stash list.
git stash apply                 // Applies the changes from the most recent stash
git stash apply [stash_name]    // Applies the changes from a specific stash.
git stash drop [stash_name]     // Removes a specific stash without applying it.
git stash clear                 // Removes all stashes from the repository.
git stash -u                    // The -u flag stashes untracked files along with changes to tracked files.
git stash -a                    // The -a flag stashes both untracked and ignored files.



// WOKING DIRECTORY <-> STAGING AREA
git diff                    // compares changes of working directory and staging area
git diff <file>             // shows the differences for a specific file in your working directory and staging area


// STAGING AREA <-> LOCAL REPOSITORY
git diff --cached               // --cached compares staging area with last commit on local repository
git diff <commit1> <commit2>    // compare the differences between any two commits (first 3-4 letters of commit hash)
git diff <branch1> <branch2>    // compares the the latest commit on branch1 with the latest commit of branch2
git diff origin/<branch> <branch>         // compares local and remote changes of specific branch


// WORKING DIRECTORY <-> LOCAL REPOSITORY
The git diff HEAD command is used to view the changes between the working directory and the latest commit of the current branch (HEAD). It helps identify any unstaged and staged changes that differ from the committed state.
The command shows changes not yet staged for commit, changes already staged for commit, along with unstaged changes.
git diff HEAD           // compares all changes (staged and unstaged) in the working directory with HEAD.




// GIT LOGS
The git log command is used in Git to view the commit history of a repository. It displays a list of commits that have been made, showing information such as the commit hash, author, date, and commit message. By default, git log shows the history of the current branch.
git log                     // Press 'q' to quit 
git log --oneline           // logs all the commits made in one line.
git log -n 5                // To view a specific number of recent commits, you can use the -n or --max-count option.
git log -help               // stuck in any command? use -help flag



// GIT RESTORE
git restore is used to discard changes in the working directory or restore files in the Git repository to a previous state. It is particularly useful for undoing changes to files or staging areas.
git restore <file>                  // RESTORE A FILE TO THE STATE OF ITS LATEST COMMIT IN CURRENT BRANCH(HEAD)
git restore .                       // Restore all files to the working directory in state of the HEAD.
git restore [options] <file>
    --worktree: Used to restore a file to the working directory (default behavior) in state of the HEAD.
    --staged: Removes the file from the staging area but keep it in the working directory.
    --source <commit>: Specify the commit you want to restore the file to. Defaults to --source=HEAD (the latest commit)
git restore --source <commit> <file>    // Restores a file to a specific commit hash
git restore --staged <file>             // Removes a file from the staging area but keeps it in the working directory
git restore --staged --worktree <file>  // Removes a file from staging area and restores it to the working directory in same state of the HEAD.



// GIT RESET
git reset is a powerful command in Git that is used to undo changes and move the HEAD (latest commit on current branch) to a specific state. It can modify the working directory, staging area or both, depending on the options provided.
It can be used to: Unstage files, Undo commits, Reset the state of the working directory
Values that can be passed to git reset: 
    commit: commit hash to move the HEAD to 
    HEAD~n: move the HEAD to n places before the current commit
    branch: The remote or local branch you want to point your HEAD to. Actions depend on the options passed

// Types of git reset
1. Soft Reset (--soft)
    Command: git reset --soft <commit or HEAD~n or branch>
    Effect: Moves the HEAD to the specified commit/branch whatever..., but does not change the staging area or the working directory. This means any changes after given commit will be staged (ready for commit).
    Useful if you want to undo a commit but keep the changes staged for further editing or re-committing.
2. Mixed Reset (--mixed)
    Command: git reset --mixed <commit> or simply git reset <commit>
    Effect: Moves the HEAD to the specified commit, resets the staging area to match given commit, but leaves the working directory unchanged. This will unstage any changes that were staged after given commit.
    Useful if you want to unstage changes without losing any modifications in the working directory.
3. Hard Reset (--hard)
    Command: git reset --hard <commit>
    Effect: Moves the HEAD to the specified commit and resets both the staging area and the working directory to match given commit. All uncommitted changes (both staged and unstaged) will be lost.
    This is a destructive operation and should be used carefully, as it can result in data loss.
git reset --soft  HEAD~4           // move HEAD back by 4 commit state. changes made after this commit are staged. Merge conflits may arise. we can --force push if its not a shared repository
git reset HEAD~1
git reset --hard HEAD~1
git reset --hard origin/main        // Resets your local main to match origin/main, discarding local commits



// GIT REMOVE
The git rm command is used to remove files from either the Working directory or the Staging area (index) in a Git repository. It ensures the removal of files is tracked by Git, so the deletion is included in the next commit.
git rm <file> <file2>...    // Deletes the specified files from the Working directory and Staging area. The file removal is staged for commit.
git rm .                    // Removes all files from working directory and staging area.
git rm *.log                // Removes all files matching the specified blob pattern from working dir and staging area
git rm --cached <file>      // Removes file from staging area but keeps it inside the working directory 
git rm -f <file>            // +Force option removes files even if its modified. The removal will be staged.
git rm -r <dir>             // -r Removes dir and all files within that directory. Also, stages their removal.
rm -rf *                    // Removes everything inside that directory
If a file being removed has uncommitted changes, Git will refuse to remove it unless -f is used. The removal must be committed to finalize it in the repository




// GIT BRANCH
The git branch command is used in Git to manage branches in a repository. Branches are a fundamental concept in Git, allowing us to work on different features, bug fixes, or experiments independently of the main codebase.
When you create a new branch in Git, it starts off as an exact copy of your current branch at the moment the new branch was created. It includes all the files, commit history, and changes that exist in your current branch at that time.
git branch                              // Lists all branches in local repository
git branch <branch>                     // Create a new branch, but doesn't switch to it
git branch -d <branch>                  // Deletes the branch locally if it has been merged with any another branch.
git branch -D <branch_name>             // Use -D delete the branch even if it has unmerged changes.
git push origin --delete <branch>       // Deletes the branch from a remote repository
git branch -m <new-name>                // Renames the current branch locally
git branch -m <old-name> <new-name>     // Rename any specific branch locally
git branch -a                           // Lists all branches (local and remote).
git branch -r                           // Lists all remote branches
git branch -vv                          // Lists the upstream branch each branch is tracking and the latest commit.
git merge <branch>                      // merge specified branch into current branch 
git branch --merged main                // check branches merged into main
git branch --set-upstream-to=<remote>/<branch>      // Links a local branch to a specific remote branch.

// Switch commands
git checkout <branch>           // Switch to specified branch
git checkout origin/master      // Switch to the master branch from remote repository in detached HEAD state
    - This command checks out the master branch from the remote repository origin without creating a new local branch. When switching to origin/master directly, Git places us in a detached HEAD(A state where the HEAD points to a specific commit instead of a branch). This means we are not attached to any branch but are working on a specific commit or state.
    - The branch with an asterisk (*) is the one HEAD is currently attached to. If we’re no longer in a detached HEAD state, we’ll see the branch name. 
    - To exit the detached HEAD state, we need to either reattach the HEAD to a branch or create a new branch from the current detached state
    - If you want to reattach HEAD where it belongs, switch to any other branch using git checkout <branch> or git switch
    - If you want to create a new branch from current state, use git checkout -b <branch> or git switch -c <branch>
git checkout -b <branch>                // Creates a new branch from the current branch and -b switches to it
git checkout -b <branch1> <branch2>     // Creates <branch1> based on <branch2> and switches to it.
git checkout -b master origin/master    // Creates master branch locally based on remote's origin/master and switch to it



// GIT REMOTE 
In Git, a remote is a reference to a repository hosted somewhere else (like GitHub, GitLab, or Bitbucket). It allows us to collaborate with others by pushing and pulling changes between our local repository and the remote repository.
git remote                      // Lists all existing remote repository
git remote -v                   // Lists all fetch and push urls for that remote repository
git remote add <remote> <url>     // Adds a new remote to the repository.
    <remote>: A nickname for the remote (e.g., origin, upstream).
    <url>: Remote repository's actual URL. 
git remote remove <remote>                        // Remove a remote from the repository
git remote rename <old-remote> <new-remote>	      // Rename an existing remote		
git remote set-url <remote> <url>       // Updates existing remote repository. Used when changing between SSH and HTTPS if SSH is not configured on a device.
git remote show <remote>                // Displays detailed information about a remote, including tracking branches.



// GIT CLONE
The git clone command is used to create a copy of a specific repository from a remote server (like GitHub, GitLab, or Bitbucket) to the local machine. It allows us to retrieve an entire project, including its history and all branches. When we clone a repository, Git automatically sets up origin as the remote pointing to the cloned repository.
git clone <repository-url>                              // clones into the directory same as project name by default
git clone --branch feature-branch <repository-url>      // clone a specific branch instead of default branch
git clone <repository-url>  <dir>                       // clone into specific directory (use . for current)



// LOCAL REPOSITORY <- REMOTE REPOSITORY
The git fetch command is used in Git to update our local repository with changes from a remote repository.
Unlike git pull, the working directory is left untouched. This allows us to review changes before merging them.
git fetch               // Downloads all updates (new commits, branches, and tags) from origin(default remote)
git fetch origin        // Downloads all updates from the remote origin.
git fetch origin <branch>   // Downloads updates from a specific branch on the remote origin.
git fetch --all         // Fetches changes from all configured remotes in the repository
git fetch --prune       // Fetches updates and removes references to remote branches that no longer exist on remote.
git fetch origin --tags         // Fetches only the tags from the remote repository.

// Inspect the fetched changes before merging them into our local branch.
git diff <branch> <remote>/<branch>  // Compares local branch with remote branch
git diff dev origin/dev              // Compare latest commit on dev with latest commit on remote's origin dev branch.
git checkout <remote>/<branch>       // Checks out the remote branch in detached HEAD state

// Important points
Regularly fetching changes ensures we have the latest commit state of the remote repository.
git fetch allows us to review and test changes before merging them into our local branch.
When branches are deleted from the remote, using git fetch --prune keeps the local references clean.



// WORKING DIRECTORY <- LOCAL REPOSITORY
The git merge command is used to combine the histories of two branches in Git. It integrates changes from one branch (source branch) into another (target branch). This is one of the most common ways to incorporate changes from different lines of development into a single branch. It Merges the changes from one branch into another branch.
git merge is non-destructive, meaning it preserves the entire history of both branches.
git merge               // merge changes from local repository to working tree
git merge <branch>      // merges the specified <branch> into your current branch *.
git merge --abort       // This resets the working directory to the state before the merge began.
git diff HEAD^ HEAD     // Compares the state before and after the merge.

// Types of Merge
Fast-Forward Merge: 
    Happens when the branch being merged is a direct extension of the current branch. Instead of creating a merge commit, Git simply moves the branch pointer forward. Use fast-forward merges for small changes
Recursive Merge (Three-Way Merge): 
    Happens when the branches have diverged (i.e., each branch has unique commits). Git combines changes from both branches and creates a new merge commit. Use three-way merges for feature branches. Press i to enter commit message
Squash Merge:
    Combines all changes from the source branch into a single commit on the target branch.
    git merge --squash feature-branch               // merge the feature-branch into current branch.
    git commit -m "Merged feature-branch with squash"




// WOKING DIRECTORY <- REMOTE REPOSITORY
The git pull command is used to fetch changes from a remote repository and integrate them into the current branch of the working directory. It’s a combination of two commands: git fetch and git merge 
git pull <remote> <branch>   // fetch and merge changes from the remote branch into the current local branch.
git pull --rebase            // --rebase replays the local commits on top of the fetched changes for a clean history
git pull --dry-run           // --dry-run simulates what would happen without actually pulling
git pull origin master --allow-unrelated-histories
    - used when we need to combine two repositories or branches that do not share a common commit history. Normally, Git does not allow merging unrelated histories, as it assumes that the repositories must have started from a shared root commit.

// When to Use --allow-unrelated-histories
Merging Two Independent Repositories: 
    If we are combining two repositories into one, their histories will be unrelated, and Git will block the merge unless this flag is used.
Reinitializing or Overwriting a Repository: 
    If we initialized a local repository (git init) and later tried to pull from an another existing remote repository, the histories would be unrelated.
Connecting Forks or Cloned Repositories: 
    If a repository was forked or cloned manually (not via GitHub or a similar platform), their commit histories might not align.

// Key Points to Remember
git pull combines fetch and merge, but if we want more control, consider using git fetch, then git merge.
When we clone a repository, Git sets up the local branch to track the corresponding branch on the remote. For example, main will track origin/main.
Configure Default Behavior: To ensure git pull uses rebase instead of merge by default: 
    git config --global pull.rebase true
Always pull the latest changes before pushing to avoid rejecting our push due to outdated commits.




// LOCAL REPOSITORY -> REMOTE REPOSITORY 
The git push command is used to upload local repository content to a remote repository. It transfers commits from your local branch to the corresponding branch on the remote repository, making your changes visible to others.
git push <remote> <branch>              // Pushes changes from a local branch to the remote branch on the remote repo
git push --all <remote>                   // Pushes all local branches to the specified remote.
git push -u <remote> <branch>           // The -u flag sets the upstream branch.
git push origin --delete <branch>       // delete a branch on remote repository
git push origin master --force          // overwrite the remote branch with your local branch forcefully

// Best Practices for Using git push
Always ensure your local branch is up to date with the remote branch. Pull any changes that may have been pushed by others before you push your own changes
Commit Often.
Use Feature Branches. Avoid pushing directly to the main or master branch. Use feature branches (feature/login-page) for new work and push those instead.
Avoid using git push --force on branches that others are working on, as this can rewrite history and cause problems for collaborators. 




// .gitignore patterns
If a file was already tracked by Git (it was added and committed to the repository before adding it to .gitignore), Git will continue tracking it, even if it's later added to .gitignore .gitignore only prevents new files from being tracked. Use git rm --cached .gitignore to remove tracking the file.
mylogs.log      // Ignores mylogs.log files in ALL dir
/mylogs.log     // Ignores mylogs.log file in main dir  ( / represents the root dir )
*               // Ignores everthing in the repository
*.txt           // Ignores all .txt files
!important.txt  // ! is used to un-ignore a file or directory that was previously ignored.
temp*/          // Ignores all directories only(not files) that start with temp (like temp1, tempTest, etc.).
**/temp         // Ignores directories and subdirectories at any level.
ignore/         // This is a FOLDER

// Errors and Solutions
Updates were rejected because the remote contains work that you do not have locally. 
Cause: Someone else might have pushed onto the remote repository.
Solution: First we need to imlement their changes first and then ours on top of them.

Merge Conflicts
Cause: Changes in the same part of a file on both branches.
Solution: Edit the file to resolve the conflict. Add the resolved file using git add -A. Commit the merge.

Merge Fails Due to Uncommitted Changes
Cause: Local changes conflict with the branch being merged.
Solution: Stash the changes using git stash. Perform the merge then reapply the stash using git stash pop.

fatal: refusing to merge unrelated histories
Cause: the commit histories of Repo1 and Repo2 do not share a common ancestor.
Solution: Use git pull with --allow-unrelated-histories flag which tells Git to ignore the fact that the histories are unrelated and proceed with merging the changes.
